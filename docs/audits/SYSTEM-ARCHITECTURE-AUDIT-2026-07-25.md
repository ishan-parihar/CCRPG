## 4. Architecture Analysis: Two Systems — Separate or Integrated?

### 4.1 The Correct Architecture: Orthogonal Systems with a Bridge

The user's intuition is correct: these are **two separate systems** that must remain separate but bridge through a specific mechanism.

```
┌─────────────────────────────────────────────────────────┐
│                    SIGNIFICATOR                          │
│                                                          │
│  ┌──────────────────┐    ┌──────────────────────────┐   │
│  │  Developmental    │    │  Knowledge               │   │
│  │  Assessment       │    │  Curriculum              │   │
│  │                   │    │                          │   │
│  │  altitudes        │    │  knowledge.conceptStates │   │
│  │  shadows          │    │  knowledge.subjectProgress│  │
│  │  drives           │    │  knowledge.studyHistory  │   │
│  │  polarity         │    │  knowledge.learningProfile│  │
│  │  transformations  │    │  knowledge.forgettingCurves│ │
│  │  theta timestamps │    │                          │   │
│  └──────────────────┘    └──────────────────────────┘   │
│           │                        │                     │
│           │    ┌──────────────────┐│                     │
│           └────│  CCI Engine      │┘                     │
│                │  (6 dimensions + │                       │
│                │   knowledgeHealth)│                      │
│                └──────────────────┘                       │
└─────────────────────────────────────────────────────────┘
                         │
                         │ CCI feeds
                         ▼
┌─────────────────────────────────────────────────────────┐
│              AUTO-MODE STRATEGY ENGINE                    │
│                                                          │
│  Session Theme: developmental + curriculum               │
│  Encounter Mix: developmental encounters + curriculum    │
│                 candidates (interleaved)                  │
└─────────────────────────────────────────────────────────┘
```

### 4.2 Why They Must Remain Separate

| Argument | Explanation |
|----------|-------------|
| **Capacity ≠ Knowledge** | A player can be at Green stage (Cognitive) but only Tier 1 knowledge in CS. Stage determines *how deeply* they can engage, not *what* they can learn. |
| **Same content, different depth** | "What is a variable?" is Tier 1 content. A Red-stage player and a Green-stage player both encounter it — but engage at different depths. |
| **Orthogonal axes** | Developmental stage is vertical (growth). Knowledge depth is horizontal (mastery). They're independent dimensions of the same player. |
| **Historical evidence** | The codebase evolved them separately — assessments in `src/core/assessments/`, curriculum in `src/core/curriculum/`. Conflating them would break the existing architecture. |

### 4.3 The Bridge Points

| Bridge | Where | What It Does |
|--------|-------|--------------|
| **CurriculumDevMapping** | `CurriculumHolon.devMapping` | Maps each holon to primaryLine + stageRange — tells the encounter scheduler which developmental line this curriculum content exercises |
| **CCI knowledgeHealth** | `CCIEngine.ts` | Curriculum progress feeds into the CCI composite score (20% weight) |
| **CurriculumBridge** | `CurriculumBridge.ts` | Bidirectional: curriculum outcomes → developmental signals, developmental needs → curriculum recommendations |
| **generateCurriculumCandidates** | `CandidateGeneration.ts` | Interleaves curriculum encounters with developmental encounters based on study theme |
| **Auto-Mode Strategy** | `AutoModeStrategy.ts` | Session plan addresses both developmental and curriculum needs |
| **Adaptive Difficulty** | `CandidateGeneration.ts` Phase 6B | Adjusts curriculum target depth based on retention and performance |

- ✅ `HolonLevel` enum (11 values including legacy compat)
- ✅ `DepthLevel` enum (7 values: absent → transformed)
- ✅ `CurriculumDevMapping` (primaryLine + stageRange)
- ✅ `Isomorphism` (cross-domain structural patterns)

But it does NOT have:

- ❌ A `FrameworkTier` type (Tier 1–4 classification)
- ❌ A function mapping `HolonLevel` → `FrameworkTier`

## 7. Integration Points Audit

### 7.1 Curriculum → Developmental Signal Flow

```
CurriculumHolon encounter
  → DualDepthResult (knowledgeDepth + developmentalSignal + metacognition)
  → CurriculumBridge.bridgeCurriculumToDevelopmental()
  → CurriculumBridgeResult {
      knowledgeUpdate: { conceptStates }
      developmentalSignals: { primaryLine, depthLevel, driveScores, shadowDetected }
      shouldTriggerShadowWork: boolean
    }
  → Significator.knowledge.conceptStates updated
  → CCI knowledgeHealth dimension recalculated
  → AutoModeStrategy adjusts session plan
```

**Status:** ✅ Fully wired. The bridge exists and handles both directions.

### 7.2 Developmental → Curriculum Signal Flow

```
Developmental encounter (shadow surface, theta decay, drive imbalance)
  → DevelopmentalNeed { type, line, urgency }
  → CurriculumBridge.bridgeDevelopmentalToCurriculum()
  → CurriculumRecommendation { conceptId, action, priority, targetDepth }
  → generateCurriculumCandidates() includes this recommendation
  → Encounter scheduler interleaves it with developmental encounters
```

**Status:** ✅ Fully wired. Developmental needs can trigger curriculum encounters.

### 7.3 CCI Integration

```
Significator (altitudes + drives + polarity + shadows + transformation + knowledge)
  → CCIEngine.computeCCI()
  → 6 dimensions: altitude, driveHealth, polarity, shadowTopology, transformationReadiness, knowledgeHealth
  → knowledgeHealth = { conceptCoverage, averageDepth, retentionHealth, integrationDensity, misconceptionLoad }
  → Weight: 20% of composite (DEFAULT_CCI_WEIGHTS.knowledgeHealth = 0.20)
```

**Status:** ✅ Fully wired. Knowledge health feeds into CCI at 20% weight.

### 7.4 Encounter Scheduler Interleaving

```
AutoModeStrategy.selectSessionTheme() → { developmental theme, study theme }
  → scheduleNext() → developmental encounters (from ModuleRegistry)
  → generateCurriculumCandidates() → curriculum encounters (from CurriculumRegistry)
  → Merge and rank by priority
  → scheduleNextWithHolonicReturn() → inject Holonic Return if needed
  → Final encounter list
```

**Status:** ✅ Fully wired. Curriculum and developmental encounters are interleaved.

## 8. Architectural Preferences (Carry Forward)

### 8.1 Non-Negotiable Principles

1. **Two systems remain separate.** Developmental assessment (64 cells) and knowledge curriculum (holon hierarchy) are orthogonal. They bridge through CurriculumBridge and CCI, not by merging.

2. **Framework-complexity is a meta-line, not a 9th line.** It determines the depth at which all 8 lines operate. It should be tracked as a dimension on curriculum holons, not as a separate assessment module.

3. **The Significator is the single source of truth.** Both developmental state (altitudes, shadows, drives) and knowledge state (conceptStates, studyHistory) live on the Significator. No separate player profiles.

4. **The CCI is the integration point.** The CCI composite score blends developmental and knowledge health. This is where the two systems meet for session-level decisions.

5. **Encounter scheduling is the delivery mechanism.** Both developmental encounters and curriculum encounters flow through the same scheduler. The scheduler doesn't know which system an encounter belongs to — it only knows priority, modality, and constraints.

### 8.2 Framework-Complexity Integration Path

The implementation path for doc 35 should be:

1. **Phase 1: Type System** — Add `FrameworkTier` type, `holonLevelToTier()` function, add `frameworkTier` to `ConceptState`
2. **Phase 2: Seed Data** — Calibrate existing 48 holons with tier-aware depth rubrics
3. **Phase 3: Scheduler** — Add tier-aware modality selection in `generateCandidates()`
4. **Phase 4: Pedagogy** — Add constructivism gradient (direct instruction → open inquiry)
5. **Phase 5: CCI** — Add cross-paradigm integration density to knowledgeHealth
6. **Phase 6: Content** — Expand seed data toward 744 holons (4 branches × 186 holons each)
