# Cognitive / Amber — Scenario-Choice Game Concept

> **Axis:** The scenario-choice axis probes cognitive intelligence through RULE-BASED DECISIONS — dilemmas where the player must apply rules to situations. At Amber, this is: "The code says X. The situation is Y. What do you do? Which rule applies? What happens when two rules conflict?"
>
> **Why this axis for Cognitive/Amber:** Concrete operational thinking includes APPLYING rules to situations — not just following them in isolation but deciding WHICH rule applies WHEN. This modality tests whether the player can navigate rule-governed decisions, revealing rigidity vs. flexibility.

---

## 1. Game Identity

- **Title:** "The Code's Dilemma"
- **Core mechanic:** The player faces situations where rules must be APPLIED — sometimes clearly, sometimes ambiguously, sometimes in conflict. "The code says honour your elder. The code says speak truth. Your elder speaks falsehood. What does the code require?" Rule-application dilemmas.
- **Duration:** 3-5 minutes per session (infinite checkpoints; fatigue-aware)
- **Internal progression:** The Clear Code → The Applied Rule → The Two Rules → The Edge Case → The Living Judge

---

## 2. The Catalyst→Experience→Integration Flow

**Catalyst:** "The code is clear. But the situation is complex. Which rule applies? What do you do when two rules point different ways? Can you THINK through the code — not just recite it?" The contact boundary is: "Can you apply rules to situations with cognitive flexibility?"

**Unconscious response:**
- *Submergent:* How does the player apply rules? The Rigid Systematiser applies the FIRST rule regardless of context ("The code says X. Done."). The Rule-Breaker ignores the code entirely ("I'll do what I want"). The Premature Theorist invents meta-rules ("The deeper principle transcends both rules"). The System-Refuser applies the rule but refuses to consider edge cases ("The rule is clear. Don't complicate it").
- *Emergent:* Can they apply rules with appropriate flexibility — following the code while navigating complexity?

**Integration path:** Rewards FLEXIBLE RULE-APPLICATION — applying the right rule to the right situation, navigating conflicts between rules, handling edge cases without rigidity or chaos.

**Successful integration:** The player can apply rules to complex situations — the decision-making foundation of concrete operational thought.

---

## 3. Drive Probing (All 4 × Both Domains)

### Agency Dark-Domain
**Context:** Making rule-based decisions independently.
- Healthy: Applies rules to situations with confidence; decides which rule fits
- Pathological: Cannot decide without authority; OR: decides rigidly without considering context
- **Detection:** Whether rule-application is sovereign and contextual

### Agency Golden-Domain
**Context:** Deciding when rules conflict (no clear authority to consult).
- Healthy: Makes a reasoned choice between conflicting rules
- Pathological: Freezes at conflict; cannot choose; OR: chooses impulsively
- **Detection:** Decision quality under rule-conflict

### Communion Dark-Domain
**Context:** Applying rules when others disagree with the application.
- Healthy: Maintains own rule-application while hearing disagreement
- Pathological: Changes application to match others; OR: rigidly refuses input
- **Detection:** Whether own rule-application survives social pressure

### Communion Golden-Domain
**Context:** Collaborative rule-application (deciding together which rule applies).
- Healthy: Contributes reasoning AND accepts others' reasoning
- Pathological: Cannot collaborate on decisions; dominates or defers
- **Detection:** Quality of collaborative rule-application

### Eros Dark-Domain
**Context:** Consistency of rule-application over time.
- Healthy: Applies rules consistently across similar situations
- Pathological: Applications are inconsistent; same situation gets different rules
- **Detection:** Rule-application consistency

### Eros Golden-Domain
**Context:** Growing sophistication (handling more complex rule-conflicts).
- Healthy: Can handle increasingly complex dilemmas as capacity grows
- Pathological: Cannot grow; OR: jumps to complexity beyond capacity
- **Detection:** Growth in rule-application sophistication

### Agape Dark-Domain
**Context:** Maintaining rule-application capacity over time.
- Healthy: Returns to rule-application tasks with maintained capacity
- Pathological: Capacity degrades; cannot apply rules after absence
- **Detection:** Cross-session rule-application stability

### Agape Golden-Domain
**Context:** Whether rule-application appears spontaneously in other contexts.
- Healthy: Applies rules to novel situations without prompting
- Pathological: Rule-application exists only in explicit dilemma tasks
- **Detection:** Spontaneous rule-application transfer

## 4. Shadow Surfacing (All 4 Quadrants)

### Dark-Addiction: "The Rigid Systematiser"
**How it surfaces:** Applies the FIRST rule encountered regardless of context. Cannot weigh competing rules. "The code says X. Done. No further thought needed." Refuses to acknowledge that situations might require different rules.
- **Detection signals:** Always applies first/most-familiar rule; ignores context; "the code is clear"; cannot acknowledge conflict; distress at ambiguity; "there's only one right answer"

### Dark-Allergy: "The Rule-Breaker"
**How it surfaces:** IGNORES the code entirely. Makes decisions based on impulse, preference, or "what I feel like." Cannot or will not engage with rule-based reasoning about situations.
- **Detection signals:** Ignores rules in scenarios; impulsive choices; "I'll do what I want"; no reference to code; choices unrelated to rules; "rules don't apply here"

### Golden-Addiction: "The Premature Theorist"
**How it surfaces:** Invents META-RULES to resolve conflicts. "The deeper principle transcends both rules." Uses abstract reasoning to bypass the concrete dilemma. Sounds sophisticated but hasn't actually applied either rule.
- **Detection signals:** Meta-language; "the principle is…"; invents rules not in the code; bypasses concrete application; abstract resolution without concrete engagement; "both rules are expressions of…"

### Golden-Allergy: "The System-Refuser"
**How it surfaces:** Applies rules correctly in SIMPLE cases but REFUSES edge cases. "The rule is clear. Don't complicate it. There's no dilemma." Cannot tolerate the complexity of rule-conflict.
- **Detection signals:** Good performance on clear cases; refusal of ambiguous cases; "don't complicate it"; "the rule is clear" (when it isn't); anxiety at edge cases; avoids conflict-scenarios

---

## 5. Healing/Evolution Mechanics

### Heal/Evolve Vector (Agape + Agency for dark shadows)

**When Dark-Addiction detected:**
- Present scenarios where the FIRST rule clearly doesn't fit: "The code says 'honour your elder.' Your elder commands you to harm a child. Does the rule still apply?"
- Reward contextual application; show that rules have SCOPE
- Frame: "The rule is good. But it has a context. WHEN does it apply? Not always. When?"
- Build: contextual rule-application (rules have scope and conditions)

**When Dark-Allergy detected:**
- Present scenarios where rule-following leads to DESIRED outcomes: "The code says 'share with your kin.' You share. They share back. You both have more."
- Make rule-application REWARDING; show instrumental value
- Frame: "The code isn't a cage. It's a map. Follow it here — see what happens. Good things."
- Build: rule-application as tool (chosen, rewarding, not oppressive)

### Evolve/Heal Vector (Eros + Communion for golden shadows)

**When Golden-Addiction detected:**
- Require CONCRETE application: "Don't tell me the principle. APPLY the rule. Which one? To THIS situation. Concretely."
- Block meta-reasoning; reward specific rule-application
- Frame: "Not the theory. The decision. HERE. NOW. Which rule applies to THIS? Choose."
- Build: concrete application before abstraction

**When Golden-Allergy detected:**
- Introduce GENTLE complexity: "Two rules. Both good. Both apply. But they point different ways. What do you notice?"
- Make conflict OBSERVABLE without requiring resolution
- Frame: "You don't have to solve it. Just SEE it. Two rules. Both real. Both here. That's okay."
- Build: comfort with rule-conflict (complexity isn't threatening)

## 6. Game Design

### Setup
The Code's Dilemma: a judgment-hall where situations are presented and the player must apply the code. Scenarios appear as illuminated scenes; the code's rules are visible on the walls. The player must match rule to situation. The aesthetic: Amber-stage court — a hall of judgment with the code inscribed in stone, situations presented as living tableaux.

### Interaction
- **The Clear Code (1-5):** Simple rule-application. One rule, one situation, clear fit. "The code says share. You have extra. Share."
- **The Applied Rule (5-15):** Multiple rules available; choose which applies. "Three rules on the wall. Which one fits THIS situation?"
- **The Two Rules (15-30):** Rule-conflict. Two rules both apply but point different ways. Navigate.
- **The Edge Case (30-50):** Ambiguous situations where no rule clearly fits. What does the code require?
- **The Living Judge (50+):** Full rule-application integration: clear + selective + conflicting + ambiguous.

### Feedback
- Contextual application → "Well judged. The right rule for the right moment. The code lives through you."
- Rigid application → "Look again. Does that rule FIT here? The code has many rules. Which one serves THIS moment?"
- Rule-ignoring → "The code is here. On the wall. Which rule speaks to this situation? Just one. Which?"
- Meta-bypass → "Not the principle. The RULE. Which specific rule applies? Point to it. Apply it."
- Complexity-avoidance → "Two rules. Both real. You don't have to solve it yet. Just see both. Both are true here."

### Difficulty Adaptation
- Clarity: obvious fit → multiple options → conflicting rules → ambiguous
- Rules available: 2 → 3-4 → 5+ (more to choose from)
- Context complexity: simple situation → multi-factor → competing needs
- Social pressure: solo judgment → others disagree → authority disagrees
- Stakes: low-consequence → moderate → high-consequence dilemmas

### Internal Progression
| Phase | Checkpoint range | What changes |
|---|---|---|
| The Clear Code | 1-5 | Simple one-rule application |
| The Applied Rule | 5-15 | Selecting from multiple rules |
| The Two Rules | 15-30 | Navigating rule-conflict |
| The Edge Case | 30-50 | Handling ambiguity |
| The Living Judge | 50+ | Full rule-application integration |

---

## 7. Item Pool Specification

### Item types
- **Clear-fit scenarios:** One rule obviously applies (warm-up)
- **Selection scenarios:** Multiple rules; player selects correct one
- **Conflict scenarios:** Two+ rules both apply but conflict
- **Edge-case scenarios:** No rule clearly fits; must reason from code-spirit
- **Social-pressure scenarios:** Others advocate different rule-application

### Minimum pool size
- 20+ clear-fit, 20+ selection, 15+ conflict, 10+ edge-case, 10+ social-pressure

### Drive/shadow mapping
- Always applies first rule → dark-addiction; ignores all rules → dark-allergy
- Invents meta-rules → golden-addiction; refuses complexity → golden-allergy

---

## 8. Scoring Rubric

### Capacity scoring
- **Application accuracy:** Does the player apply the correct rule to the situation?
- **Contextual sensitivity:** Do they consider context when multiple rules are available?
- **Conflict navigation:** Can they acknowledge and navigate rule-conflicts?
- **Flexibility:** Do they adjust application based on situation features?
- **Consistency:** Are similar situations handled similarly?

### LLM rubric
- **Medium:** Scenario presentation and response evaluation require LLM. Must assess: rule-application accuracy, contextual sensitivity, rigidity indicators, meta-bypass detection. Rubric-guided with specific shadow indicators.

---

## 9. Technical Requirements

### Input types
- Tap/select (choose which rule applies); text/voice (explain reasoning — optional); drag (match rule to situation)

### Timing requirements
- Decision latency tracked; no time pressure; deliberation time noted (very fast = impulsive; very slow = frozen)

### NPC/AI requirements
- Scenario generation system (situations with varying rule-applicability)
- Rule-conflict system (scenarios where multiple rules apply)
- Response evaluation (accuracy of rule-application)
- Difficulty adaptation (clarity, complexity, social pressure)

### LLM requirements
- **Medium:** Scenario generation, response evaluation, contextual sensitivity assessment. Core rule-matching can be partially algorithmic but nuanced scenarios require LLM.

### State persistence
- Decision history; accuracy per scenario-type; rigidity indicators; flexibility metrics; conflict-navigation quality; meta-bypass frequency; complexity-avoidance frequency; drive/shadow signals; checkpoint position
